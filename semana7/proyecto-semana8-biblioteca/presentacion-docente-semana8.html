Proyecto: Biblioteca Hibrida

Objetivo de la clase: explicar una solucion completa que integra herencia, polimorfismo, interfaces, colecciones genericas, instanceof y organizacion por paquetes.

Herencia Polimorfismo Interfaces Generics instanceof Arquitectura basica

1. Contexto del negocio

En lugar de repetir el mismo dominio academico de siempre, el proyecto modela una biblioteca hibrida que administra materiales fisicos y digitales.

  • Materiales fisicos: se pueden prestar y devolver.
  • Materiales digitales: se pueden descargar y reproducir como muestra.
  • Todos comparten datos comunes: titulo, codigo y autor.

Este dominio es ideal porque permite demostrar que una clase puede heredar una base comun y, ademas, implementar distintas capacidades mediante interfaces.

2. Resultados de aprendizaje que cubre

  • Diseñar una jerarquia de clases reutilizable.
  • Aplicar herencia con extends.
  • Aplicar polimorfismo con una referencia comun.
  • Integrar interfaces como contratos de comportamiento.
  • Usar colecciones genericas para almacenar objetos heterogeneos.
  • Validar tipos en tiempo de ejecucion con instanceof.

4. Teoria central: herencia

La herencia modela una relacion del tipo "es un".

public abstract class MaterialBiblioteca {
    private final String titulo;
    private final String codigo;
    private final String autor;

    public abstract void mostrarResumen();
}

Las subclases:

  • LibroFisico es un MaterialBiblioteca
  • RevistaFisica es un MaterialBiblioteca
  • Ebook es un MaterialBiblioteca
  • Audiolibro es un MaterialBiblioteca

Ganancia: atributos comunes y un metodo abstracto compartido, evitando repeticion innecesaria.

5. Teoria central: interfaces

Una interfaz no representa tanto que es un objeto, sino que puede hacer.

public interface Prestable {
    void prestar();
    void devolver();
    boolean estaPrestado();
}
public interface Descargable {
    void descargar();
}
public interface Reproducible {
    void reproducirMuestra();
}

Lectura docente:

  • LibroFisico y RevistaFisica implementan Prestable.
  • Ebook y Audiolibro implementan Descargable.
  • Ebook y Audiolibro tambien implementan Reproducible.

Esto muestra por que una interfaz es mas flexible que meter todo en una unica clase base con metodos absurdos para todos.

6. Relacion entre herencia e interfaces

LibroFisico extends MaterialBiblioteca implements Prestable
RevistaFisica extends MaterialBiblioteca implements Prestable
Ebook extends MaterialBiblioteca implements Descargable, Reproducible
Audiolibro extends MaterialBiblioteca implements Descargable, Reproducible

Aqui conviven dos ideas:

  • Herencia: todos son materiales de biblioteca.
  • Interfaces: cada uno puede tener capacidades distintas.

Ese es el punto fino: una clase puede pertenecer a una jerarquia y, ademas, asumir multiples roles.

8. Teoria central: polimorfismo

El polimorfismo aparece cuando tratamos objetos distintos usando una referencia comun.

Catalogo<MaterialBiblioteca> catalogo = new Catalogo<>();

Esto permite almacenar libros, revistas, ebooks y audiolibros en la misma estructura.

for (MaterialBiblioteca material : catalogo.obtenerTodos()) {
    material.mostrarResumen();
}

La llamada correcta se resuelve en tiempo de ejecucion segun el tipo real del objeto.

9. Teoria central: colecciones genericas

La clase Catalogo<T> encapsula una lista tipada y reutilizable.

public class Catalogo<T> {
    private final List<T> elementos;

    public void agregar(T elemento) { ... }
    public List<T> obtenerTodos() { ... }
}

Valor pedagógico:

  • Introduce reutilizacion real mediante generics.
  • Evita acoplar el catalogo a un solo tipo concreto.
  • Permite escalar la solucion si mañana el negocio cambia.

10. Teoria central: instanceof

Se usa para validar el tipo real en tiempo de ejecucion cuando necesitamos aplicar una accion especial.

if (material instanceof Prestable prestable) {
    prestable.prestar();
}
if (material instanceof Ebook) {
    System.out.println(material.getTitulo() + " es un Ebook.");
}

Interpretacion docente:

  • La interfaz me permite saber si el objeto tiene cierta capacidad.
  • El tipo concreto me permite afinar la logica cuando realmente lo necesito.

Advertencia elegante: usar instanceof esta bien, pero abusar de el puede ser senal de diseno flojo.

11. Flujo del sistema

1. Main crea un GestorBiblioteca.
2. GestorBiblioteca carga datos demo en Catalogo<MaterialBiblioteca>.
3. Main solicita mostrar catalogo.
4. GestorBiblioteca recorre la coleccion y ejecuta mostrarResumen().
5. Main solicita procesar prestamos, descargas y muestras.
6. GestorBiblioteca usa instanceof para detectar capacidades:
   - Prestable
   - Descargable
   - Reproducible
7. Main solicita mostrar tipos reales.
8. El sistema informa si cada elemento es Ebook, Audiolibro o material fisico prestable.

14. Justificacion de diseño

  • No todo material se presta, por eso Prestable no va en la superclase.
  • No todo material se descarga, por eso Descargable es una interfaz separada.
  • No todo material reproduce muestra, por eso Reproducible tambien se separa.
  • Esto evita meter metodos absurdos en una clase base comun, como un descargar() vacio en un libro fisico. Y menos mal.

15. Ventajas didacticas del proyecto

  • El dominio es facil de entender para estudiantes.
  • Las interfaces representan capacidades claras del negocio.
  • El uso de instanceof tiene sentido real y no se siente forzado.
  • La estructura por paquetes permite enseñar orden, responsabilidad y legibilidad.
  • El proyecto es pequeno, pero suficientemente rico para discutir decisiones de diseño.

16. Preguntas para trabajar con estudiantes

  1. ¿Por que Ebook no deberia implementar Prestable?
  2. ¿Que pasaria si metieramos descargar() dentro de MaterialBiblioteca?
  3. ¿En que parte aparece realmente el polimorfismo?
  4. ¿Para que se usa instanceof y por que no conviene abusar de el?
  5. ¿Que ganamos con Catalogo<T> en vez de usar una lista directa?

17. Posibles extensiones

  • Agregar usuarios y prestamos asociados.
  • Agregar reservas.
  • Agregar multas por retraso.
  • Persistir datos en archivo.
  • Agregar menus interactivos.

Es decir: el proyecto ya sirve como base para evolucionar sin tener que botarlo y empezar de cero. Eso, casualmente, es una senal de que el diseño no quedo tan mal.

18. Cierre docente

Este proyecto demuestra una idea central de la programacion orientada a objetos:

La herencia sirve para compartir estructura comun.
Las interfaces sirven para modelar capacidades.
El polimorfismo permite tratar objetos distintos de forma uniforme.
instanceof permite validar tipos reales cuando hace falta.
Las colecciones genericas hacen que todo eso sea util a escala.

En otras palabras: aqui las interfaces no son adorno teorico. Son una herramienta concreta para construir software mas flexible y mas limpio.
